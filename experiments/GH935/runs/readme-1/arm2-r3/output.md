This tool runs a command, but only when no other copy of that command is already running. You give it three things: a path to use as a lock file, a number of seconds after which it should treat an existing lock file as abandoned, and the command to run. It creates the lock file, runs the command, and deletes the lock file once the command finishes. It passes the command's exit status back to you. If the lock file already exists and is recent, the tool exits straight away with a status of 0, and it never runs the command.

That fits periodic jobs that you start from cron or a systemd timer, such as a backup, a sync, or an index rebuild. When one run takes longer than the gap between runs, the next run finds the lock and exits, so two copies never write to the same place at once. Missing a run costs you nothing here, because the timer will start another one shortly.

A run that dies without deleting its lock file would otherwise block every run after it, and the stale timeout is what clears that lock. The tool measures the timeout from the moment the run started, and nothing refreshes it while the run continues. So set the timeout longer than the longest run you expect. If you set it too short, a second copy will delete the lock of a run that is still going, and then both copies run together.

Reach for something else when a skipped run is a problem. If you want the second run to wait its turn rather than disappear, use `flock`, which can block until the lock frees. If you need to tell a skipped run from a successful one, this tool won't show you the difference, because it exits 0 either way. If your copies run on separate machines against a shared filesystem, use a lock service instead, because exclusive file creation is not dependable there.
