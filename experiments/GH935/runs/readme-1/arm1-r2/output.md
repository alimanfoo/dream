This tool runs a command only if no other copy of it is already running. You give it a lock file, a staleness threshold in seconds, and the command line. If it can create the lock file, it runs your command, waits, removes the lock, and exits with the command's own status. If the lock file already exists and was created recently, it does nothing and exits zero. If the lock file is older than the threshold, it assumes the previous holder died without cleaning up, removes the lock, and takes over.

It is built for periodic jobs — cron entries, systemd timers, launchd plists — where a run that overlaps the previous one is worse than a run that never happens. Backups, mirror syncs, index rebuilds, log rollups: work that is idempotent over time but corrupting or merely wasteful when doubled. Reach for it when the schedule is tighter than the worst-case runtime, and when skipping a tick costs nothing because the next tick picks up the same work.

Two properties decide whether it fits. Skipping is silent and successful; cron sees exit zero and sends no mail, so if you need to know a run was dropped, log that yourself. And the lock's timestamp is written once, when the lock is taken, and never refreshed while the command runs. Set the threshold comfortably above the longest run you can imagine. Set it too low and a second copy will steal the lock from a perfectly healthy process and run beside it, which is the exact failure you installed this to prevent.

Look elsewhere when you need queuing rather than skipping — flock blocks by default and is the standard answer on Linux. Look elsewhere when the lock must hold across machines or live on a network filesystem, and when you want leases, heartbeats, and a visible history of what ran. Those belong to a scheduler or a lock service, not to a twenty-line wrapper.
