It runs a command only when no other copy of that command is already running, and does nothing at all when one is. You give it a lock file path, a staleness threshold in seconds, and the command to guard. It tries to create the lock file exclusively. If the file already exists and was created more recently than the threshold, the tool exits quietly with status zero and runs nothing. If the file is older than that, it assumes the previous holder died without cleaning up, removes the file, and takes the lock itself. Once the command finishes, the lock file is deleted and the command's own exit status is passed straight through.

It is meant for anyone with a repeating job on a single machine: a cron entry, a systemd timer, a git hook, a polling loop in a shell script. The case it serves is the one where two copies running at once is worse than one copy not running at all. Mirror syncs, backups, index rebuilds, log shipping, cache warmers — work that is idempotent, scheduled often, and cheap to skip, because another run is due shortly anyway.

Reach for something else in several situations. If the second invocation should wait its turn rather than give up, use `flock(1)`, which blocks. If you need to know that a run was skipped, this tool will not tell you; a skip and a clean success both exit zero, and nothing is written to stderr. The staleness clock starts when the lock is taken and is never refreshed while the command runs, so a threshold shorter than the command's worst-case runtime lets a second copy break in and run concurrently — set it well above the longest run you expect. The lock is a file on one filesystem on one host, so it coordinates nothing across machines; use a database advisory lock or a dedicated lock service for that. And if you want queueing, retries, backfills or dependencies between jobs, you want a scheduler, not a wrapper.
