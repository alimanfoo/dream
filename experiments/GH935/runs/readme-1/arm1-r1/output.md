This tool runs a command only if no other copy of that command is already running. You give it a lock file path, a staleness timeout in seconds, and the command itself. If it can create the lock file, it runs your command, waits, cleans up the lock, and exits with whatever the command exited with. If the lock is already there and recent, it exits zero immediately and runs nothing at all. If the lock is there but older than the timeout, it assumes the previous run died without cleaning up, removes the lock, and takes it.

It is for people with a crontab and a job that must not overlap with itself: a backup that occasionally runs long, a sync that pulls from a slow remote, an indexer whose runtime depends on how much work arrived. The scheduler keeps firing on its fixed interval; this makes the extra firings harmless.

Reach for it when dropping a run is the right response to congestion. The semantics here are skip, not queue — a run that finds the lock held is gone, not deferred, and nothing records that it happened. That suits periodic work where the next tick will catch up anyway, and suits it badly where every invocation carries its own payload.

Reach for something else in a few cases. If you have `flock` from util-linux, prefer it: the kernel releases its locks when the process dies, so it has no staleness problem to configure and no window in which the wrong answer is possible. The timeout here is a real trade-off — set it shorter than your job's worst-case runtime and a slow run will have its lock stolen, leaving two copies running and the first to finish deleting a lock it no longer owns. If you need mutual exclusion across machines, use something built for that; `O_EXCL` on a shared network filesystem will not give you it. And if you need to know afterwards whether the job ran, add that logging yourself, because a skip and a success look identical from the outside.
