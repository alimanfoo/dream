This tool runs a command only if no other copy of it is already running. It takes the path of a lock file, a staleness timeout in seconds, and the command. When it can create the lock file, it runs the command and deletes the lock file afterwards, and it exits with the command's own status. When the lock file already exists and was changed within the timeout, the tool exits straight away with status zero, and the command never runs.

A skipped run counts as success, and that is what makes the tool useful under cron. A job that fires every minute but sometimes takes three minutes will otherwise start a second copy on top of the first. Wrap the job in this tool and the extra runs drop silently, so cron sends no mail and your monitoring stays quiet.

A process that dies without cleaning up leaves its lock file behind, and every later run would then skip forever. The timeout covers that case. Once the lock file's modification time is older than the timeout, the next run deletes the file and takes the lock. Nothing refreshes that time while the command runs, so set the timeout longer than the longest run you expect. If a run does outlast the timeout, the next run takes the lock and starts a second copy alongside it, which is the overlap you were trying to prevent.

Reach for something else when skipping is the wrong answer. If the second run has to wait its turn rather than drop, use `flock`. If a skipped run must be recorded, queued or retried later, use a job runner that keeps a history of runs. If the job runs on several machines against shared storage, this tool cannot help you, because the lock is a file on one machine's own filesystem and only guards the copies that share it.
